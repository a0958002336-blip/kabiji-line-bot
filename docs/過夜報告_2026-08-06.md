## 四、B+ 報錯設計（老闆要求記錄理由，醒來 review）

**做了什麼**：`attendanceQuery` 走 M/D 路徑時，若月 <1 或 >12、日 <1 或 >31 → 直接回明確錯誤：

```
⚠️ 日期看不懂：「26/07」
・單日：查出勤 7/16
・區間：查出勤 7/1-7/15
・整月：查出勤 7月（也可用 2026/07、本月、上月）
```

**為什麼要加**：老闆要求測「查出勤 26/07 確認不會被誤判成 26月7日」，但**只做 B 解決不了**——
B 的守衛嚴格要求 4 位數年份，「26」只有 2 位，仍會走 M/D 路徑算成 26 月 7 日，然後靜默回
「目前沒有紀錄」。而「靜默回沒有紀錄」這個失敗模式，當天已經坑了兩次（月份查詢、`2026/07`），
判斷該一次處理掉。

**為什麼不做「26/07 自動當成 2026/07」**：會與 M/D 慣例打架——`7/26` 是 7 月 26 日，
`26/07` 卻變年月，同一種寫法兩套規則，比現在更難懂。**若老闆想要這個行為，請明講，我再改。**

**判定範圍**：只擋月 >12、日 >31。**刻意不做每月天數校驗**（`2/30` 會放行），
只擋明顯不可能的值，避免誤擋。

**觸發時機**：僅在 `dates.length` 為真時檢查，月份路徑不受影響；在 `parseYMD` 之前 `return`，
不產生垃圾區間。

**已知侷限（既有行為，未改）**：`_bad` 只檢查 `dates[0]` / `dates[1]`，
打三個以上日期時第三個之後會被忽略——原本就只取前兩個。

恆為真、永遠 PASS，等於白佔一條。
**解法**：改為真實比對 `rep.indexOf('03/15') === -1`（去年 3/15 那筆不應出現）。
因 `fmtTime` 只印 `MM/dd` 不含年份，故以日期辨識。改完仍 PASS，但這次是真的驗到東西。
**這是我自己發現並修的，不是測試失敗。**
